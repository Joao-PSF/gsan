## 2. O que estava errado na ADR proposta

SSR tratado como **autorização por rota** · SPA tratada como **JWT** e como origem da autorização por caso de uso · CSRF como motivo para escolher arquitetura · **uma API para tela e integração** · híbrido como **dois modelos de autorização** · "o modelo de autorização muda junto com a interface" · relatório reduzido a "bytes × URL assinada" · canais limitados a usuário interno e integrações. Detalhe em [ADR-0007 §3](../decisoes/0007-arquitetura-de-interface.md).

## 3. A decisão

**Aceita** — [ADR-0007](../decisoes/0007-arquitetura-de-interface.md): **C — híbrido por canal, com o backoffice no padrão D** (server-driven + aprimoramento progressivo), sob a regra *apresentação é adaptador; regra de negócio e autorização pertencem aos casos de uso*.

| Canal | Padrão |
| ----- | ------ |
| Backoffice | HTML no servidor · atualização parcial por fragmentos · JS só em ilhas · sem SPA, sem *build* de frontend obrigatório |
| Portal | Canal próprio; padrão por omissão igual; frontend independente só por critério registrado |
| Integrações · campo · GIS | Contratos explícitos, autenticados, versionados; nunca endpoint de tela nem banco interno |
| Relatórios | Solicitar e obter artefato são casos de uso autorizados — corrige D-03 |
| Analytics | Fatos e projeções publicados |

**Etapa 1**: Spring MVC com HTML no servidor, atualização parcial e sessão com CSRF. A biblioteca concreta é escolhida na Etapa 0, dentro do padrão.
